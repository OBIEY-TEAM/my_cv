# NOM DU PROJET : "Luka Mosala SaaS" - Générateur Automatisé de Candidatures Sur Mesure
# DESTINATAIRE IA : Jules AI / Agent IA Autonome de Développement

---

## 1. VISION DU PROJET & OBJECTIF GÉNÉRAL
Construire la plateforme SaaS complète **Luka Mosala** (Mobile Flutter + Web React Client + Dashboard Admin Angular + Backend Django REST Framework) connectée aux API d'Intelligence Artificielle (Jules / OpenAI / Claude) et aux passerelles de paiement Mobile Money (Airtel Money, MTN Mobile Money, PayDunya).

L'application permet à tout utilisateur d'importer une offre d'emploi (via un lien URL, un fichier PDF ou un texte brut), une photo de profil et son profil/CV de référence (style README/markdown), puis de générer instantanément un dossier de candidature complet et sur mesure :
1. **CV Professionnel sur mesure (PDF - Strictement 1 page)** avec photo recadrée professionnellement.
2. **Lettre de Motivation personnalisée (PDF - Strictement 1 page)** structurée et rédigée selon l'offre.
3. **Email de candidature rédigé (.txt)** prêt à copier-coller.
4. **PDF de l'offre d'emploi originale** archivée.
5. **Arborescence de dossiers organisée** par site/organisme et intitulé de poste.

## 2. ARCHITECTURE TECHNIQUE GLOBALE DU SYSTÈME

```
 [ APPLICATION MOBILE FLUTTER WEB ]    [ WEB CLIENT REACT ]    [ DASHBOARD ADMIN ANGULAR ]
 (mobile-luka-mosala.onrender.com)   (client-luka-mosala.onrender.com) (admin-luka-mosala.onrender.com)
                 │                             │                              │
                 └─────────────────────────────┼──────────────────────────────┘
                                               │ (APIs REST / JSON / JWT)
                                               ▼
                           [ BACKEND DJANGO REST FRAMEWORK / PYTHON ]
                             (backend-luka-mosala.onrender.com)
                                 │             │               │
                 ┌───────────────┘             │               └───────────────┐
                 ▼                             ▼                               ▼
   [ BASE POSTGRESQL / REDIS ]   [ AGENT IA / JULES API ]   [ PAYMENTS FINTECH ]
    (Données Users, Subscriptions) (Génération CV/LM/Email)   (Airtel Money, MTN MoMo)
```

### A. Backend : Django REST Framework (DRF) + Python
- **API RESTful sécurisée :** Authentification JWT (SimpleJWT), CORS, throttled endpoints.
- **ORM & Base de données :** SQLite / PostgreSQL, Redis pour le caching.
- **Tâches Asynchrones & Queues :** Celery / Redis pour le scraping des offres web et la génération de PDF lourds sans bloquer l'API.
- **Intégration GitHub / Jules AI API :**
  * Service de synchronisation avec GitHub via Octokit / Git Python API.
  * Webhooks & appels API vers l'agent IA (Jules API / LLM) pour analyser l'offre et générer le contenu du CV, de la Lettre de Motivation et de l'Email.
- **Génération de PDF :** Moteur Python ReportLab / WeasyPrint pour générer des PDFs au design moderne respectant strictement la limite d'1 page.
- **Paiements Mobile Money :** Module d'intégration Webhook / REST avec les API Fintech (Airtel Money Congo, MTN Mobile Money Congo, PayDunya, SankMoney).

### B. Application Mobile : Flutter / Flutter Web
- **Multiplateforme :** iOS, Android et Flutter Web (déployé sur Render).
- **Gestion d'État :** BLoC / Provider / Riverpod.
- **Fonctionnalités Clés :**
  * Appareil photo intégré (Camera Plugin / Image Picker) pour capturer la photo de profil en direct ou choisir depuis la galerie.
  * Module de recadrage intelligent de photo de profil (Crop 1:1 buste/visage avec espace au-dessus de la tête).
  * Upload de fichiers (PDF d'offres d'emploi, Markdown README de profil).
  * Lecteur PDF natif pour prévisualiser le CV et la Lettre de Motivation générés.
  * Téléchargement & Partage direct (Share Plus, File Saver).

### C. Application Web Client : React.js / Vite / TypeScript
- **UI/UX Moderne :** Tailwind CSS, Shadcn/UI, Lucide Icons, Framer Motion.
- **Dashboard Réactif :**
  * Glisser-déposer (Drag & Drop) pour les fichiers d'offres et photos.
  * Éditeur Markdown / WYSIWYG pour éditer son profil README et ses compétences.
  * Prévisualisation en direct (Live PDF Preview) du CV et de la Lettre de Motivation.
  * Historique des candidatures et statut des paiements.

### D. Web Admin & Dashboard Organisateur : Angular 17+
- **Gestion Administrative :**
  * Supervision des utilisateurs, gestion des abonnements, validation des transactions Mobile Money.
  * Monitoring de la consommation des API IA et statistiques de génération de CV/Lettres.

### B. Gestion des Erreurs Courantes & Auto-Correction
En cas de page blanche, d'erreur serveur, ou d'erreur spécifique du type :
> `Blocked request. This host ("luka-mosala-web.onrender.com") is not allowed. To allow this host, add "luka-mosala-web.onrender.com" to preview.allowedHosts in vite.config.js.`

L'agent IA doit exécuter la procédure d'auto-correction suivante :
1. **Ouvrir et corriger la configuration Vite (`site_client_react/vite.config.js` ou `vite.config.ts`) :**
   ```javascript
   export default defineConfig({
     preview: {
       allowedHosts: ['luka-mosala-web.onrender.com', 'client-luka-mosala.onrender.com', '.onrender.com', 'all']
     },
     server: {
       allowedHosts: ['luka-mosala-web.onrender.com', 'client-luka-mosala.onrender.com', '.onrender.com', 'all']
     }
   })
   ```
2. **Corriger la configuration CORS / ALLOWED_HOSTS du backend Django (`settings.py`) :**
   ```python
   ALLOWED_HOSTS = ['backend-luka-mosala.onrender.com', 'luka-mosala-web.onrender.com', '.onrender.com', 'localhost']
   CORS_ALLOWED_ORIGINS = [
       "https://client-luka-mosala.onrender.com",
       "https://luka-mosala-web.onrender.com",
       "https://admin-luka-mosala.onrender.com",
       "https://mobile-luka-mosala.onrender.com"
   ]
   ```
3. **Commit et Push immédiat** sur la branche de déploiement (`jules-8374694265899943435-377d46a8`).
4. **Revisiter le site** `https://luka-mosala-web.onrender.com` dès que le déploiement est vert sur Render, prendre une nouvelle capture d'écran et valider le bon fonctionnement jusqu'à l'obtention d'un résultat visuel 100% fonctionnel et conforme.

## 1. RAPPEL DES CONCEPTS DE L'API JULES

L'API Jules (alpha) est construite autour de 3 ressources REST, authentifiées via le header
`X-Goog-Api-Key`, à la base URL `https://jules.googleapis.com/v1alpha` :

- **Source** : le dépôt GitHub connecté (ex: `sources/github/<owner>/<repo>`).
- **Session** : une unité de travail asynchrone confiée à l'agent (équivalent d'une conversation
  de tâche continue), créée via `POST /v1alpha/sessions`.
- **Activity** : chaque événement à l'intérieur d'une session (plan généré, message, résultat),
  consultable via `GET /v1alpha/sessions/{session}/activities`.

Endpoints clés à utiliser :
- `GET /v1alpha/sources` — lister les dépôts connectés
- `POST /v1alpha/sessions` — créer une session de travail (champs : `prompt`, `sourceContext`,
  `title`, `automationMode` optionnel — ex: `AUTO_CREATE_PR`, `requirePlanApproval` optionnel)
- `GET /v1alpha/sessions` — lister/paginer les sessions (`pageSize`)
- `POST /v1alpha/sessions/{session}:approvePlan` — approuver un plan si `requirePlanApproval=true`
- `POST /v1alpha/sessions/{session}:sendMessage` — envoyer un message dans une session existante
- `GET /v1alpha/sessions/{session}/activities` — suivre la progression

⚠️ L'API est en alpha : Jules IA doit prévoir une gestion d'erreurs tolérante (schémas et champs
susceptibles d'évoluer), journaliser les réponses brutes en cas d'échec de parsing, et ne jamais
bloquer le flux applicatif principal si l'API Jules est indisponible (dégradation gracieuse).

---

## 2. NOUVELLE APP DJANGO DÉDIÉE : `jules_integration`

En complément des apps déjà listées dans le prompt maître (`users`, `profile_manager`, `jobs`,
`subscriptions`, `ai_engine`, `pdf_generator`), créer une app dédiée :

```
backend/jules_integration/
├── clients.py        # Client HTTP encapsulant les appels à jules.googleapis.com
├── models.py          # JulesSession, JulesActivity (traçabilité locale)
├── serializers.py
├── services.py        # Logique métier : create_session, send_message, approve_plan, poll_activities
├── views.py            # Endpoints internes exposés au Frontend/Admin (proxy sécurisé, jamais la clé API côté client)
├── urls.py
└── tests.py
```

### Modèles à prévoir
- `JulesSession` : `session_id` (id distant), `source`, `title`, `prompt`, `status`,
  `automation_mode`, `require_plan_approval`, `created_at`, `updated_at`, lien vers l'utilisateur
  admin/dev à l'origine de la session.
- `JulesActivity` : `session` (FK), `activity_id`, `type`, `payload` (JSON brut), `created_at`.

### Client HTTP (`clients.py`)
- Utiliser `requests` (ou `httpx`) avec timeout explicite, retry limité (ex: 3 tentatives,
  backoff exponentiel) et gestion des codes 401/403/429/5xx.
- Header d'authentification : `X-Goog-Api-Key: <valeur lue depuis la variable d'environnement>`.
- Ne jamais logger la clé API en clair dans les logs Django.

### Endpoints internes exposés (réservés au rôle Admin/Superutilisateur du Dashboard Angular)
- `POST /api/jules/sessions/` → crée une session Jules (proxy vers `POST /v1alpha/sessions`)
- `GET /api/jules/sessions/` → liste les sessions locales + statut synchronisé
- `POST /api/jules/sessions/{id}/approve-plan/` → proxy `:approvePlan`
- `POST /api/jules/sessions/{id}/send-message/` → proxy `:sendMessage`
- `GET /api/jules/sessions/{id}/activities/` → proxy + persistance locale des activités
- Documenter chacun de ces endpoints avec `@extend_schema` (drf-spectacular), conformément à la
  section Swagger déjà définie dans le prompt maître.

### Sécurité
- Ces endpoints ne doivent jamais être accessibles à un utilisateur candidat standard : restreindre
  via une permission DRF dédiée (`IsAdminOrSuperUser`).
- La clé API Jules ne transite jamais vers le Frontend React ni vers l'App Mobile Flutter : tous
  les appels passent exclusivement par le backend Django (pattern proxy).

## 4. CONFIGURATION SQLITE POUR LES TESTS SUR RENDER

Le prompt maître prévoit déjà `USE_SQLITE=True` comme variable d'environnement du service
`backend-luka-mosala` sur Render (voir `render.yaml`, section 3). Pour les tests liés à
l'intégration Jules :

1. **Environnement de test dédié** : dans `settings.py`, si `USE_SQLITE=True` (ou si
   `DJANGO_SETTINGS_MODULE` pointe vers un module de test), forcer la base de données sur
   SQLite (`django.db.backends.sqlite3`, fichier `db_test.sqlite3`) plutôt que PostgreSQL, afin
   de permettre l'exécution rapide des tests CI sur Render sans dépendance à une base managée.
2. **Tests unitaires `jules_integration`** :
   - Mocker systématiquement les appels réseau vers `jules.googleapis.com` (via `responses`,
     `unittest.mock.patch`, ou un client HTTP factice) — ne jamais appeler l'API Jules réelle
     pendant les tests automatisés.
   - Couvrir : création de session (succès/échec), approbation de plan, envoi de message,
     pagination des activités, gestion des erreurs 401/429/5xx, absence de clé API configurée.
3. Ajouter dans `env.example` la variable de test suivante pour permettre de basculer explicitement
   les tests en mode mock :

```env
JULES_API_MOCK_MODE=True
```

Quand `JULES_API_MOCK_MODE=True`, le client `clients.py` doit retourner des réponses simulées
(fixtures JSON) au lieu d'appeler le réseau — utile pour les previews PR sur Render où la clé
API réelle ne doit pas être exposée.

## 1. TRAITEMENT CENTRALISÉ EN SESSION UNIQUE JULES IA SUR GITHUB

- **Toutes les requêtes d'une exécution doivent être envoyées dans une SEULE et MÊME SESSION Jules IA**.
- Le code source du backend réside directement sur GitHub (pas de passage par une API externe pour le code source).
- L'administrateur de la plateforme déclenche l'exécution manuellement en connectant Jules au dépôt GitHub et en configurant l'automatisation des Pull Requests (PRs).

---

## 2. DOSSIER `COMMANDES` & ARBORESCENCE DE SYNCHRONISATION EN BASE DE DONNÉES

Le backend Django doit synchroniser automatiquement les données saisies par les utilisateurs en base de données vers le dossier `/COMMANDES` à la racine du projet :

```
/COMMANDES
├── INFO/               # Fichiers texte TXT des profils utilisateurs
│   ├── <ID_UNIQUE_1>.txt
│   ├── <ID_UNIQUE_2>.txt
│   └── ...
└── PHOTO/              # Photos de profil PNG des utilisateurs
    ├── <ID_UNIQUE_1>.png
    ├── <ID_UNIQUE_2>.png
    └── ...
```

### Règle d'association et nommage :
- **ID Unique :** Chaque utilisateur possède un `<ID_UNIQUE>` généré par le backend.
- Le fichier profil texte `COMMANDES/INFO/<ID_UNIQUE>.txt` contient la totalité des données structurées de l'utilisateur (Info avec Nom, Prénom, Genre, Date de naissance, Numéro principal, Numéro secondaire, Résumé pro, Adresse, Pays, Arrondissement, Quartier ; Expériences ; Certifications ; Diplômes ; Projets).
- La photo `COMMANDES/PHOTO/<ID_UNIQUE>.png` porte exactement le même `<ID_UNIQUE>` que le fichier textuel correspondant.

---

## 3. DOSSIER `RESULTAT` & DÉLIVRABILITÉ AUX CLIENTSS PAYANTS

- L'agent Jules lit les fichiers `COMMANDES/INFO/<ID_UNIQUE>.txt` et `COMMANDES/PHOTO/<ID_UNIQUE>.png`.
- Jules génère l'ensemble des livrables de candidature sur mesure et enregistre les résultats dans le dossier `/RESULTAT` à la racine du projet :

```
/RESULTAT
└── <ID_UNIQUE>/
    ├── <NOM_SITE_1>/
    │   └── <INTITULE_POSTE_1>/
    │       ├── CV.pdf
    │       ├── LETTRE_DE_MOTIVATION.pdf
    │       ├── OFFRE_EMPLOI.pdf
    │       └── EMAIL.txt
    └── <NOM_SITE_2>/
        └── <INTITULE_POSTE_2>/
            ├── CV.pdf
            ├── LETTRE_DE_MOTIVATION.pdf
            ├── OFFRE_EMPLOI.pdf
            └── EMAIL.txt
```

### Service des fichiers par le Backend Django :
- Le backend Django récupère les fichiers générés dans `/RESULTAT/<ID_UNIQUE>/`.
- **Accès restreint :** Le backend sert ces fichiers (téléchargement PDF / texte Email) **EXCLUSIVEMENT aux utilisateurs qui ont réglé leur facture / abonnement** (`payment_status = approved`).
